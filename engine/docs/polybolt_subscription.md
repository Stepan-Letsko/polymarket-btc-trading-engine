# PolyBolt — connection & subscription reference

How to connect to Polymarket's PolyBolt websocket, log in, and subscribe to
the two BTC reference-price channels we record. PolyBolt replaces the old
RTDS relay.

**Endpoint:** `wss://ws-live-v2.polymarket.com/ws`

Like the CLOB feed, the URL is generic. Unlike the CLOB feed, the channels we
use are **gated**: the connection has to log in with CLOB API credentials
before the server will accept a subscription.

> Written from Polymarket's documentation and the official machine-readable
> contract (`https://ws-live-v2.polymarket.com/asyncapi.json`, PolyBolt
> 2.0.0), read on 2026-11-02. The connection sequence, `authed` and
> `subscribed` replies were then confirmed against real traffic from
> `polybolt_ws.cpp` the same day. Close codes and error handling are still
> from the docs only.

## Why these channels: what resolves the market

The `btc-updown-5m-*` markets resolve on **Chainlink's BTC/USD TWAP 60-second
stream** (Gamma's `resolutionSource` for every window is
`https://data.chain.link/streams/btc-usd-twap-60s-streams`):

> resolves to "Up" if the time-weighted average price (TWAP) of Bitcoin,
> generated by Chainlink, of the time range specified in the title is
> greater than or equal to the price at the beginning of that range.

So we record:

| Channel | Filter | Why |
|---|---|---|
| `price.crypto.twap` | `{"symbol": "btcusd", "window_seconds": 60}` | **The resolution feed.** Ground truth for every window. |
| `price.crypto` | `{"symbol": "btcusd"}` | Chainlink's raw (spot) BTC/USD price that the TWAP averages. Moves before the TWAP does. |

`price.crypto` btcusd defaults to Chainlink. We do not pin a `provider` (see
[Provider pinning](#provider-pinning) for why).

## Connection sequence

Every connection — the first one and **every reconnect** — goes through the
same conversation. Nothing carries over from a previous connection: login,
subscriptions and sequence numbers all start fresh.

```
open connection
  → send  {"op":"auth", ...}
  ← recv  {"op":"authed"}                       (or an error ack - see below)
  → send  {"op":"subscribe", ...}               (both channels in one batch)
  ← recv  {"op":"subscribed","channel":"price.crypto.twap",...}
  ← recv  price.crypto.twap snapshot            ("snapshot": true)
  ← recv  {"op":"subscribed","channel":"price.crypto",...}
  ← recv  price.crypto snapshot                 ("snapshot": true)
  ← recv  live updates, one per second per channel ...
```

That's the order observed in real traffic: each channel's ack is followed
straight away by its own snapshot. Don't rely on it, though — handle each
message by what it is, whatever order they come in.

Wait for `authed` before subscribing. A subscribe that arrives first is
rejected with `auth_required` (the connection stays open; authenticate and
resend).

The server closes a connection that has neither authenticated nor
subscribed within **120 seconds** (close `4008`, reason `unengaged`).

## 1. Authenticate

```json
{
  "op": "auth",
  "rid": "a1",
  "auth": {
    "apiKey": "<POLY_API_KEY>",
    "secret": "<POLY_SECRET>",
    "passphrase": "<POLY_PASSPHRASE>"
  }
}
```

| Field | Required | Meaning |
|---|---|---|
| `op` | **yes** | `"auth"` |
| `auth.apiKey` / `auth.secret` / `auth.passphrase` | **yes**, all three | CLOB L2 API credentials — the same trio used for the CLOB user websocket and order placement. An incomplete set answers `bad_op`. |
| `rid` | no | Our own request id. The server echoes it on the reply, so we can tell which request a reply belongs to. |

Success:

```json
{"op": "authed", "rid": "a1"}
```

**Max 8 auth frames per connection** — the 9th gets `auth_attempts` and the
connection is closed (`4008`). Never retry auth in a tight loop.

### Credentials

Read from environment variables `POLY_API_KEY`, `POLY_SECRET`,
`POLY_PASSPHRASE` — never written in code. Locally they live in
`engine/.env` (git-ignored) and are loaded into the shell before
starting the program:

```bash
set -a; source .env; set +a
```

On the server, systemd provides them from a protected file instead. The auth
frame is something we **send**, and we only record what we **receive**, so
credentials never end up in a recording. Never print them, including under
`--verbose`.

## 2. Subscribe

Both channels in one batch frame (a batch counts as one request against the
rate limit):

```json
{
  "op": "subscribe",
  "rid": "s1",
  "subscriptions": [
    { "channel": "price.crypto.twap", "filter": { "symbol": "btcusd", "window_seconds": 60 } },
    { "channel": "price.crypto",      "filter": { "symbol": "btcusd" } }
  ]
}
```

| Field | Required | Meaning |
|---|---|---|
| `op` | **yes** | `"subscribe"` |
| `subscriptions` | **yes** | Array of `{channel, filter}` pairs, at least one. |
| `filter.symbol` | **yes** | Lowercase symbol, `"btcusd"`. |
| `filter.window_seconds` | **yes** on `price.crypto.twap` | Must be `60`. Other windows are accepted but carry no data. |
| `rid` | no | Echoed on every ack this frame produces. |

Each new subscription gets a `subscribed` ack and then **one snapshot** (the
previous two minutes of prices). Subscribing again to a `(channel, filter)`
already active returns another ack but **no** new snapshot.

### Unsubscribe

Same shape with `"op": "unsubscribe"`; the server confirms with
`unsubscribed`. We don't need it — we subscribe once per connection and keep
both channels for its whole life.

### Provider pinning

`price.crypto` filters accept an optional `"provider": "chainlink" | "pyth"`.
We leave it out: the default for btcusd is already Chainlink. The contract
says the server's provider selector is disabled by default, but our
`subscribed` acks **do** carry `"provider":"chainlink"`, which means it's
enabled — and confirms Chainlink is what's served. Whatever happens, every
payload names its real producer in `source` — check that rather than
assuming.

## Heartbeat

- The **server** sends a websocket-level ping every **25 seconds**. Standard
  clients (IXWebSocket included) answer with a pong automatically. **Two
  missed pongs** close the connection with `4002`.
- Optionally, the client can send `{"op": "ping"}` (an application-level
  ping, as JSON — not the plain-text `PING` the CLOB feed uses). The server
  answers `{"op": "pong"}`.

## Limits

| Limit | Value | On breach |
|---|---|---|
| Active subscriptions per connection | 64 `(channel, filter)` pairs | `sub_limit` error, then close `4008` |
| Subscribe / unsubscribe frames | 20 per second (a batch counts once) | `rate_limited` error, then close `4008` |
| Frame size | 64 KB | close `4008` |
| Auth frames per connection | 8 | `auth_attempts` error, then close `4008` |
| Unengaged connection | 120 s without auth or subscription | close `4008`, reason `unengaged` |

## Close codes and reconnecting

The close code says **why** the server closed us, and the right reaction
differs. Reconnecting blindly is wrong for several of them.

| Code | Meaning | What to do |
|---|---|---|
| `4001` | Authentication failed on a presented credential | **Don't** retry as-is: fix the credentials first. |
| `4002` | Slow consumer, or pong timeout | Retry with exponential backoff and jitter. If it repeats, we're not keeping up. |
| `4003` | Server draining (restarting) | Reconnect **once** after a uniformly random 0–10 s delay. |
| `4008` | Policy violation (a limit above) | **Don't** reconnect blindly — fix the request that caused it. |
| `1008` | Access-token auth expired | Applies to Access-Token logins only, not CLOB credentials. |
| `1006` | Abnormal disconnect (network drop) | Exponential backoff with full jitter: start at 1 s, cap at 30 s. |

If the connection is refused with HTTP `429` or `503`, wait at least the
`Retry-After` time, plus jitter.

"Jitter" = adding a random amount to each wait, so that thousands of clients
dropped at the same moment don't all reconnect at the same instant.

After any reconnect: authenticate again, resend both subscriptions, seed
state from the new snapshots, and re-read `source`.
